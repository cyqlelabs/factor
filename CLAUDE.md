# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Conventions

Commit messages follow [Conventional Commits v1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) (`feat:`, `fix:`, `docs:`, `test:`, `chore:`, …).

## Commands

```bash
make check                                  # gate: vet + race tests + coverage ≥90% + gofmt check
go test ./internal/evals                    # the behavioural evals (scripted, no API key)
go test ./internal/agent -run TestName      # single test
make test-race                              # race detector (needs CGO_ENABLED=1; everything else is CGO-free)
make cover                                  # statement coverage, fails under 90%
make lint                                   # golangci-lint (.golangci.yml) — its own CI job, so `make check` alone is not enough
make hooks                                  # point git at .githooks, so every commit lints before it lands
make build                                  # local binary
make build-tiny                             # -tags nobrowser strips the CDP browser suite (stubs in internal/browser/browser_stub.go)
make diagrams                               # re-render docs/assets/*.mmd into the PNGs the docs embed (needs node)
```

The coverage gate is real: new code needs tests or `make check` fails. Live tests (real headless Chrome, real desktop round-trip) auto-skip in `-short` mode or when the machine can't host them; the rest of the suite runs against fakes — scripted providers, a fake smrti sidecar and a fake voice shell (both spawned by re-execing the test binary), a fake Telegram API, a fake carrier, a scripted microphone and speaker, a fake MCP server over real stdio JSON-RPC, and a scripted desktop backend.

Grid vision is covered end to end at two levels, both of which locate the target and read the grid **out of the rendered pixels** rather than from the grid code, so an overlay or translation that is wrong cannot agree with the test:

- `internal/desktop/grid_live_test.go` — a private Xvfb with solid-color blocks at known screen positions; the real helpers capture and the real `xdotool` moves the pointer, which must land inside the block. Covers coarse pointing, a small target only the zoom pass can hit, region zoom, a downscaled frame on a big screen, and re-grounding after the screen changes. Needs Xvfb, scrot, xdotool and xlogo. Locally, missing helpers skip. In CI the install is not best-effort: it is bounded and retried, and a failure fails the job, because a release whose desktop path was never exercised should not be a green tick. The tests can still skip for other reasons — `-short`, no usable display, xlogo refusing to start — so "the helpers installed" is not yet the same claim as "the live tests ran".
- `internal/agent/vision_loop_e2e_test.go` — the whole turn with no display: real loop, registry, desktop tools and provider over a local HTTP server, with a fake vision model that decodes the PNG that actually crossed the wire, names a cell, and clicks it. Runs everywhere, so the CI boxes where the live tests skip still cover the path.

## Architecture

Factor is a single static Go binary (`cmd/factor`): a desktop AI agent with long-term memory, reachable over CLI or Telegram. `internal/app` is the composition root — it wires everything below into one `App` shared by the CLI modes and the `factor gateway` daemon (`internal/gateway`, which adds PID-file management, cron, and heartbeat). `factor gateway -d` re-spawns the gateway detached (own session on unix, no console on Windows), confirms startup through the pid file the child claims, and leaves its output in `~/.factor/gateway.log`. While the gateway runs in a desktop session, `internal/tray` shows a systray icon whose menu is a live status overview — version, uptime, memory health, connected channels, a row each, read from `gateway.StatusLines` on every menu open plus a slow tick — above a quit item that stops it cleanly (`gateway.RequestStop`); the tray is pure Go on Linux (StatusNotifierItem over the session D-Bus — no bus, no icon, nothing else changes) and Windows, and stubbed elsewhere because a macOS tray needs cgo the CGO-free builds cannot carry. The icon is the Factor mark rasterized in code (`icon.go`, from the brand artboard's own geometry — PNG, or ICO on Windows), so no asset ships in the binary and a test decodes exactly what the tray will draw; it is handed over before `systray.Run` on Linux, whose StatusNotifierItem properties are exported from whatever systray already holds — set from inside `onReady` it loses that race and the item registers an empty pixmap — and from inside `onReady` on Windows, where there is no window to hang it on any earlier. The tray owns the main goroutine; the gateway serves from a goroutine beside it.

Message flow:

```
channels → bus → agent loop → provider chain
                     └→ tool registry ─ every tool suite
memory recall injects into each turn's context; turns are stored back after
jobs / cron / heartbeat publish results onto the bus, re-entering sessions proactively
```

- **`internal/bus`** — bounded queues decoupling connectors from the loop. Publishing never blocks; a full queue drops loudly. `OutboundMessage.Interim` marks a note sent while its turn is still running, so a channel can treat it differently from the reply that follows. `bus.External` is the one rule for whether a channel is somewhere Factor can reach the user unprompted — the CLI, `system` and `cron` are not — and every proactive sender (heartbeat, cron results, release and restart notices) addresses the last external chat, which `internal/agent` keeps in `~/.factor/last-channel.json` so a fresh process is not mute until the user speaks first. That address only counts while a connector is running for it: the gateway hands the loop `Manager.Serves` (`Loop.SetReachable`), so a chat whose channel is switched off is withheld rather than reported as delivered and then dropped by the pump.
- **`internal/channel`** — connectors self-register via `channel.Register(name, factory)` in package `init()`, keyed to their own raw-JSON config section. Telegram is the model implementation. Two optional capabilities exist for connectors that need them: `Typer` (typing indicator) and, for synchronous conversations, `TurnRunner` + `Toolset`, wired by the gateway. A `TurnRunner` may also declare `Steerable`, which says its replies come back through its own `Send` as well: `channel.BindTurns` then binds it to `Loop.ProcessDirectSteering` rather than `ProcessDirectNotice`, so a turn it starts on a busy session folds into the live one instead of queuing behind it. Voice declares it; the phone deliberately does not, since an answer published to the bus there is dialled as a second call rather than spoken on the line the caller is holding.
- **`internal/channel/phone`** — voice: real phone calls and SMS. Turns bypass the bus — a localhost OpenAI-compatible bridge (`/v1/chat/completions`, SSE) drives `Loop.ProcessDirectNotice` under `phone:<E.164>`, so hanging up cancels the turn. What the agent says on its way to an answer is streamed into the live call as an early content delta, ahead of the reply; off the line an interim is dropped, being worth neither a text nor a second call. A supervised Python sidecar (Patter, `voiceshell.py`, embedded via `go:embed`) owns the carrier and the speech pipeline. Factor spawns the speech process with `ORT_DISABLE_TELEMETRY=1` (`speechEnv`), and the script sets it again at module level for a run that did not come from Factor: onnxruntime posts OS build, CPU model, memory, network type, a persistent device id and the interpreter path (which holds the username) to Microsoft as it initializes, and `disable_telemetry_events()` cannot stop it — those events are logged while the environment is created, before any call can be made against it (onnxruntime#25573). The switch has to exist in the environment before the interpreter starts, which is why it lives in the spawn rather than in the script's logic. The carrier is Twilio or Telnyx (`carrier` in the config): each has its own credentials, its own wire format for synthesized audio, and its own hangup call, and on Telnyx the shell also attaches the number to the Call Control Application and points its webhook at itself on every start (Patter only auto-configures Twilio). SMS goes straight to the carrier's REST API from Go (`carrier.go`).
- **`internal/channel/voice`** — PC voice: the machine's own mic and speakers. Audio rides helper programs (`parec`/`paplay` preference chains, no cgo) through the `Env` seam; VAD, wake-word gating, and barge-in are pure Go. Each utterance runs synchronously through the bound `TurnRunner` under `voice:local`, so a barge-in cancels the in-flight turn and discards playback — no wake word asked even in wake-word mode, because a barge is spoken over the agent's own voice, which makes the wake word the word transcription mangles most — while one the transcriber hears nothing in resumes the reply where it paused. A sentence the gate turns away is answered with a soft two-note chime (`chime.go`) rather than a word, since a spoken line would be the agent replying to an utterance it just decided was not for it, and would come back through the microphone as its own voice. The player knows it for a tone rather than a voice, so talking across it is not a barge and still needs the wake word — though it is sound in the room like any other, so the microphone's bar rises for it and a recording it landed in is not read for a voice; it never takes the speakers from a reply, and it holds off `chimeCooldown` between chimes, because the gate turns away every sentence of a conversation held in front of the machine and a tone per sentence is a metronome. `ignored_chime` turns it off. The channel also remembers what it just sent to the speakers (`echo.go`): an utterance the agent's own voice was in the air for is matched against those words, so feedback loud enough to clear the raised barge bar is recognized and dropped — or stripped down to the user's words around it — instead of becoming a turn the agent holds with itself. That test is deliberately wider than "this was a barge": a user who starts a sentence in the pause before the reply lands still has the microphone segment open when the speakers begin, so the whole reply is recorded *behind* their words while nothing about the segment's opening looks like an interruption. Overlap is therefore tracked across the whole segment rather than at its start, the agent's runs are removed wherever they fall rather than only from the front, and the reply's words stay matchable for `silence_ms` past the last sound — the segment carrying the tail of a reply has not closed yet, so forgetting them the moment the speakers fall quiet threw them away a beat before the echo arrived. `playing` likewise outlasts the playback helper by `playbackTail`, since the helper exits when the sound server has the audio and not when the room has heard it. `output_volume` scales the synthesized voice for rooms where the speakers overpower the microphone, and `speech_server.speech_speed` paces it — Piper's own `length_scale`, how long each phoneme is held, rather than resampling the audio, which would slow the words down and drop the pitch with them; it is the managed server's default, so it reaches the phone as well, and a request naming its own OpenAI-style `speed` overrides it. With `speaker_id` on (it needs the managed speech server), each utterance is read over `/v1/audio/voices`, which answers with **one embedding per person in the recording** rather than one for the clip. That distinction is the feature, not a refinement of it: the segmenter closes an utterance on `silence_ms` of quiet and two people talking to each other leave far shorter gaps, so their whole exchange arrives as a single recording — read as one voice it is a blend that lands on whichever profile it is nearest, handing both people that one name while reporting a room with one person in it. The server diarizes first (pyannote's segmentation-3.0 in ONNX, ~30 ms an utterance, alongside the embedding model it already loads), embeds each person's speech alone with the gaps and every overlap removed, and returns them in the order they first spoke. A track only counts as a person if it says something nobody else was saying at the time: the segmentation model reports concurrent tracks, and on a short recording it routinely opens a second one wholly inside the first — a hypothesis about overlap, not somebody else in the room. Taking that at face value is worse than ignoring it, because subtracting its range from the speaker it sits inside punches a hole through the middle of the one voice really there, and the disconnected fragments left behind embed as nobody. The turn belongs to whoever opened the recording — the activation gate only let it through because the wake word was at its front or it answered inside the follow-up window, so anyone who joined partway through is the room, not the asker. Each voice is matched against the persistent profiles in `~/.factor/voice-speakers.json`: the owner — the first voice enrolled — and unknown voices keep `voice:local`, a recognized guest holds their own session (`voice:local:<name>`) and is named as the turn's speaker, an utterance too brief to read inherits whoever was already talking and renews that window rather than measuring it from the last utterance long enough to identify — a conversation under way is mostly short replies, and measuring from the last long one is how the person who never stopped talking becomes nobody mid-sentence, `unknown_speaker` chooses between auto-enrolling a new voice and leaving it anonymous, and the `voice_speakers` tool renames whoever spoke last, which is how a profile born "speaker-2" becomes "Roxana". On top of identification, `room.go` tracks *who is within earshot* — the question confidentiality actually turns on. Three seconds of a voice that is not the owner's, added up over a two-minute window, make the room shared — one sound cannot, because every lone unknown voice that flipped the room in three weeks of logs was a cough, a shout or a transcriber hallucination, none of them three seconds long — as does any recording holding more than one voice with a second of speech of its own, by arithmetic rather than acoustics: at most one of them can be the owner, so the rest are company, which holds even when none of them could be named and even before anyone is enrolled. That is the reading confidentiality can least afford to get wrong, and it is exactly the owner-plus-a-brief-guest case that used to read as an empty room. at which point every turn, the owner's included, runs in one session (`voice:local:room`, a slug reserved against speaker names) under a shared audience, so the private thread stays out of a context the room can hear and the people present are answered as one conversation rather than several. The evidence comes from every utterance the microphone resolves, **including the ones the activation gate turns away**: someone talking to you rather than to Factor is still someone in the room, and that audio was already captured and transcribed before being discarded. Speech is the word that matters, though — audio the transcriber returned nothing for, or returned a subtitle credit for, holds no person and is never read. Nearly a fifth of what the detector opens transcribes to nothing, and reading it named somebody off a door slam and could declare the house shared on the strength of it. That read is side-effect-free (`presenceOf`) — no enrollment, no profile learning, no sticky speaker — because ambient chatter is the wrong teacher for all three. The tracker is deliberately asymmetric: a few seconds of speech declare company, only `room_timeout_minutes` of silence or the `room` tool takes it back, since a room wrongly called shared costs a coy answer and one wrongly called private says a secret to a guest. Sound can only report people who make it, so the `room` tool is how someone who entered silently or left is declared — the model is the sensor for what gets said out loud. The room outlives the process in `~/.factor/voice-room.json`, aged against the wall clock on load rather than against uptime: a config change and an upgrade both re-exec the gateway, and coming back up private while the guest is still on the sofa would be the expensive error made by the most ordinary event on the machine. What was last announced is saved beside the occupants, so a restart neither repeats "we're not alone now" nor swallows the "on our own again" owed when somebody left during the downtime. Every flip is spoken once before the answer that depends on it and carried on the `voice heard` line, `/health` and the tray row, because a silent switch is untrustworthy in both directions. Audio the agent's own voice was in the air for is never read at all — it holds a person and a synthesizer, and belongs to neither — and inherits the conversation's current speaker instead. Above that, three length bars rise with what is at stake, measured in seconds of actual speech: 1.0 s to put a name to a voice, 2.0 s to fold it into that profile, 3.0 s to create one. Naming risks a single misattributed sentence; teaching moves the centroid every later match is judged against; a spurious profile never goes away, competes for every future match, and is how a household of three ends up with fifteen voices. Teaching also requires that the match sat comfortably above the threshold, not merely over it — and neither teaching nor minting may happen at all unless the recording held one voice, since the recording most likely to have been split wrongly is exactly the one with two people in it, and a profile outlives the mistake. A guest heard beside the owner is still told apart; they get a profile the moment they say something on their own. **Every number here is measured, and every model in the catalogue has been checked against recordings whose speakers are known** — same-person scores strictly above different-person ones, never assumed from a model card. On real utterances off a USB microphone the default model puts one person between 0.48 and 0.69 against themselves and every impostor under 0.14, which is where `speaker_threshold` at 0.35 comes from. That number is a floor, not the whole test. How much a similarity is worth depends on how much voice produced it: across 221 real matches here the score climbs with the reading — under 1.5 s, 18% of true matches fall below 0.50, and past 6 s none do — while a different person has been measured within 0.45 of a profile. So the bar rises toward 0.15 above the threshold as a reading shortens (`unsure`), and a match must also sit clear of the second-closest profile (`ambiguous`), because two profiles neck and neck is a coin flip that also drags them together. Both are unreadable moments rather than strangers: they inherit whoever was already talking, exactly as a too-short reading does, and neither moves the store. That check is not a formality: the two WeSpeaker exports this once shipped fail it outright, scoring the vendor's own verification pairs no better than chance — two different people above 0.7 while two recordings of one person sat at 0.2 — so they were removed rather than merely demoted, because a knob that produces garbage is a trap. `speech_server.speaker_model` picks among the three that pass. The store records which model made its vectors and clears itself when that changes, because two models' embeddings are not comparable and a carried-over profile would answer nothing while its owner is silently enrolled a second time. Every decision says so in the log: the `voice heard` line carries the speaker, which branch named them (`match`, `enrolled`, `unknown`, `ambiguous`, `unsure`, `overlap`, `short`, `unavailable`), the similarity it was judged on, and the session the turn ran in, so "it answered as the wrong person" is a readable line rather than a guess; at `log_level: debug` a `speaker scores` line adds every profile's similarity, which is what `speaker_threshold` is tuned against. A note the turn makes on its way to the answer is spoken as it happens, queued against the answer behind it, so a minute of tool calls does not sound like a hang. The speech tiers are the phone's — same cloud providers spoken from Go, or the managed local server via `phone.SpeechServer` on its own port (8728) — with the same probe-and-fall-back at startup. A loopback control endpoint (8730) takes `factor talk` push-to-talk, which also overrides a misfired wake word; `voice_write` (via the `Addresser` capability) delivers written replies to the terminal or the last external chat. The CLI builds this one channel itself in `runChat`, so the mic works without the gateway, and feeds the TUI bar a live meter (`Voice.Meter`: level, floor, digital-silence flag, speaking). The wizard picks the capture device from `pactl`'s source list and verifies it live (`MeasureMic`) — a source delivering exact zero is the wrong-device signature, also surfaced at runtime on the control endpoint's `/health` and as a log warning.
- **`internal/agent`** — the loop enforces **one live turn per session key** (`channel:chatID`). A second message arriving mid-turn becomes *steering*: injected between tool iterations under the same lock that guards turn release, and leftovers are republished as fresh inbound. That holds for a connector running its own turn too, and it is the difference between a spoken question answered and one answered never — a turn queued on the claim says nothing, logs nothing, and is cancelled by the next thing the user says, so the first question is lost rather than delayed. Two things still wait rather than steer: a caller that must return its own reply (`ProcessDirectNotice` — the phone, cron, jobs), and a message that reaches more people than the running turn was claimed for. That second rule is confidentiality, not politeness: a private turn recalls private memory, and folding a shared-room question into it would answer out of that context in front of whoever just walked in. Text the model emits alongside its tool calls is the agent saying what it is about to do: it goes out as `PhaseNotice` while the tools run rather than at the end of the turn. A bus-driven channel gets it from `Manager.Interim`; a connector that runs its own turns (voice, phone) gets it straight from the turn instead, through the `notice` callback `ProcessDirectNotice` threads into `channel.TurnFunc` — the one place the line arrives while it is still true, and the reason a spoken turn spent in tools is audible progress rather than dead air. A request is assembled in one order and it is the order that makes a long session affordable: system prompt, rolling summary, the conversation so far, then everything only this turn knows, then what the user just said. A prompt cache reuses the longest byte-identical prefix, so wherever two consecutive turns first differ, everything behind it is prefilled again — and recall injected into the system prompt put that difference a few hundred tokens in, which left the whole conversation uncacheable and made every turn of a long session slower than the last. `SystemPrompt` therefore takes no arguments and must not vary by turn, channel or session; `TurnContext` carries what does — recalled memories, the clock, how long the user has been away, `channelBriefing`, and the tool rules restated — on one **user** message, since the Anthropic dialect hoists every system message to the head of the request and would silently undo the placement. It is framed as machinery so it is not read as the user speaking, and it is never persisted. The tail is also where a per-turn instruction is actually read: identity and the persona open the prompt, `operatingRules` closes it, and what grows without bound sits in the middle where recall is worst. But closing the system prompt only makes those rules the head of the *request*, and the head is the one position that does not move while the conversation grows behind it — which is why a long session ends up ignoring the tools it has: the pattern of the last twenty exchanges is nearer than the paragraph telling it to check. So past `rulesFadeAt` of history the handful of rules that decay first — settle it with a tool rather than from memory, work the web in the browser, send slow work to `job_start` — are said again at the end of `TurnContext`, after `channelBriefing` and last of all. That order settles a real clash: on voice and phone the briefing is an instruction to be brief and conversational, repeated every turn from the strongest position there is, arguing against stopping to use a tool. The briefing is for where the reply comes out, which is not always where the turn runs: a heartbeat runs under `system` and a scheduled task under `cron`, and both are delivered to the last chat the user used — so the turn carries that chat as `ToolContext.Outlet` and is briefed for it on top of its own, and where the outlet is a synthesized voice, for the language that voice speaks (`channel.Localized`, wired through `Loop.SetLanguage`), since a history-less turn has no user message to take the language from and the English it falls back to is noise read in a Spanish accent. A spoken turn moves the last-chat address exactly as a written one does.

  Measured across real sessions, 79-91% of the bytes in a history are tool results — the pages the agent read, not the conversation the user had. `mask.go` replaces every tool result older than the last few with a stub naming the call that produced it, on the assembled copy only, so what was dropped can be fetched again by repeating the call while the transcript on disk stays whole. Recent results and the fact that a call failed both survive. It runs when the request is assembled and again, through `trimInFlight`, on any iteration where the turn in flight has grown past the budget: twenty tool iterations at four thousand tokens a result is more than the whole ceiling, and a turn left to grow behind a single masking pass ran past it with nothing noticing until the provider refused the request. A turn inside its budget is never touched — reading eight files to compare them needs all eight. `compact.go` handles the rest at turn-safe boundaries, budgeted against the whole request rather than the history alone: the system prompt and every tool schema are a fixed five-figure cost that used to sit outside the budget entirely. The ceiling is the smaller of `agent.summarize_at_percent` of the model's window — the cost catalog answers per model, `agent.context_window_tokens` only ever shrinks that answer (0 means auto) — and `agent.max_context_tokens`, a working ceiling far below any current window because quality decays with input length long before a window fills. Compaction runs after the turn that triggered it and again on an idle sweep, so a conversation left in the morning is tidy before the user comes back rather than tidied in front of them, and the messages it drops are appended to `<session>.archive.jsonl` instead of deleted: what replaces them in context is a summary written by a model, which is the one part of this system that cannot be trusted to be complete. A tool result carrying images (`tools.Result.Images`, e.g. `screen_view`'s annotated screenshot) rides a follow-up user message — the one placement every vision dialect accepts — with only the newest 2 frames kept in the in-flight context and only a text placeholder persisted to session history.

  Two calls the user never reads — the compaction summary and the induction verdict — can run on their own chain (`provider.utility`), sharing the ledger and the caps. One summarizes text the model has already seen and the other answers SKIP or LEARN, which is not work the top of a model range is for; unset, both run on the conversation's chain, because a summary is what replaces a session's history and nobody should inherit a weaker model for it by upgrading.

  The loop also learns from its own work (`induce.go`; `agent.learn_skills: false` turns it off): a turn that took four or more tool calls to answer is remembered — or two, if the user steered it mid-flight, since steering is the cheapest feedback this system gets and the only kind nobody has to be asked for: it says the first approach was wrong and names the right one, in the user's own words, while the work is still happening, and the induction prompt is told so the skill captures what worked rather than the detour — most recent per session, its trajectory rendered and bounded at the moment it ends — and once the session has sat quiet the idle sweep spends one metered call, billed to that session, asking whether the trajectory holds a workflow worth keeping. The reply is categorical, SKIP or LEARN, parsed rather than trusted; a LEARN lands as a `learned: true` skill in the workspace catalog, where the next turn's prompt lists it like any other skill. Induction may update its own output but never a skill somebody wrote or installed — `skill_write` drops the marker on rewrite, which is how a learned skill graduates out of induction's reach — and the learned library is capped, so past the cap the model must update or skip rather than mint near-duplicates.
- **`internal/evals`** — the behavioural half of verification. The test suite is excellent at the deterministic half — race detector, 90% coverage gate, a private Xvfb driving real helpers against real pixels — and what actually steers Factor is its prompt, which is not code with a return value and so had no test at all. An eval is a case rather than an assertion: an inbound message, a scripted model that decides what to do from the request as it actually crossed the seam, and checks on the trajectory that followed. The provider is a fake and the tools are real, so the suite needs no API key and runs in seconds. The invariants it holds are the ones nothing else would notice breaking: the system prompt is byte-identical across turns and sessions, the turn context arrives as a *user* message, cache breakpoints land where ADR-002 says, skills are listed but not inlined, the operating rules are restated past `rulesFadeAt`, every offered tool has a description and a schema, an old tool result is stubbed while recent ones survive whole, an image rides a user message and is not persisted, a budget cap comes back as a sentence, and the path guard refuses a read outside the workspace. CI reports the pass rate, which is the number to watch across a prompt change.
- **`internal/trace`** — what a turn actually did, as one JSONL record per turn under `~/.factor/traces` (ADR-003). Factor knew all of this and kept none of it: phase changes went to one live watcher and were dropped, the registry remembered only the tools that panicked, and the meter stored two integers. The record carries the models that answered with their token and cache split, the tools with duration and outcome, the events that only exist in aggregate (failover, overflow, steering), and how the turn ended; priced spend with no turn open — an idle compaction, an induction verdict — gets a record of its own, because spend nobody asked for is the spend worth being able to find. It is local, retention-bounded and never leaves the machine, and it records what a tool was *called* rather than what was said to it: arguments hold the user's paths and searches, and the shape of a turn is what the questions need. `trace.record_args` opts in and scrubs through the registry's own secret filter. The one exception is a call that failed, which keeps the first line of what the tool said back (`ToolCall.Fault`, bounded, scrubbed): that is the tool's text rather than the user's, and a breach in the error rate cannot be diagnosed without it — a rate names no tool and no cause.
- **`internal/bands`** — deterministic drift detection over those records: tool error rate, turn failures, cost and seconds per turn, failovers, overflows, and the cache hit rate, which is the one metric where a *fall* is the problem because it is the only signal that the request prefix stopped being byte-stable. Mean and standard deviation over a rolling baseline against the last hour, with a direction per metric and **no model involved**; a flat baseline or too few samples says nothing rather than everything. It feeds the heartbeat, which could previously only notice what the user thought to write into `HEARTBEAT.md`: a breach now starts a check with the numbers stated and the conclusion left open, so the model is spent judging whether an unusual reading matters instead of confirming that nothing happened. Nothing here acts on its own — every tier ends in a log line, a sentence in the heartbeat's prompt, or the user's attention. A breach also carries its evidence (`Breach.Evidence`): the calls that failed and what they said, and each failing tool's record over the whole baseline, which is what tells an hour's bad luck from a feature that has never worked on this machine. The first real breach showed why: handed a rate alone, the model grepped the journal, which holds no tool outcomes, and called "transient" a fast path that had failed every one of its calls. The heartbeat (`internal/heartbeat`) renders that evidence, tells the check to repair with the levers it owns — `config_set` to switch off what never works, `upgrade`, `pkg_install`, and never an `exec` that kills a supervised sidecar — before it reports, and keeps each verdict in `~/.factor/heartbeat-verdicts.jsonl` so the next check on the same metric reads what was said last time and a fault that keeps coming back is seen to keep coming back rather than judged fresh each time.
- **`internal/vcs`** — an opt-in local git history of the workspace (`agent.version_workspace`). Factor's own prompt is compiled into the binary and versioned with it; the user's half — `AGENTS.md`, `SOUL.md`, `USER.md`, `HEARTBEAT.md`, `instructions/` and the skill library — had none, so six months of tuning a persona left no diff and no way back, and induction writes into that same library unasked. Commits happen on every skill write, install, removal and induction. `sessions/` is excluded because transcripts churn on every message and would bury what is worth reading, and `config.json` is deliberately not versioned at all: it holds API keys by design, and a diff is not worth copying them into git objects for.
- **`internal/provider`** — a failover `Chain` of candidates. `openai.go` speaks every OpenAI-compatible dialect (OpenRouter, Ollama, Groq, …); `anthropic.go` is native. `classify.go` decides retry vs. failover vs. compaction; `reasoning.go` translates one reasoning config into each provider's dialect. `Message.Images` attaches images to user messages, translated per dialect (content-parts with data URIs vs. base64 source blocks); plain messages keep bare-string content. `Message.CacheMark` is where the caller says a stretch of the request is likely to repeat, which the Anthropic dialect turns into a `cache_control` breakpoint and the implicitly-cached dialects ignore (ADR-002) — caching there is opt-in per request, so the prompt ordering below was paying its whole cost and collecting nothing until the marks existed. `Usage` carries the cache read and write counts as subsets of `PromptTokens`, normalized across two dialects that disagree about what a prompt token is, which is what lets `internal/cost` price a hit at a tenth rather than at full rate.
- **`internal/cost`** — what a turn costs. The meter wraps the provider chain, so every call the loop makes — the visible ones, the wrap-up, the compaction summary — is priced and billed to the session whose tool context it carried. Prices come from the model catalog OpenRouter publishes, cached in `~/.factor/pricing.json` and refreshed on a daily tick, with config overrides on top and locally served models free by construction (the endpoint decides, not just the type); a model nothing prices is counted in tokens rather than guessed at, and the usage report names it. The cache split is priced too — a read at a tenth, a write at a premium — so a well-cached session stops being over-reported, and the hit rate rides the usage report because it is the only alarm for a prefix that quietly stopped being byte-stable. Totals live in `~/.factor/usage.json` — session, day, month, all-time, per model — merged into the file on every write rather than overwriting it, so a gateway and a terminal spending at once do not erase each other. Caps are checked before the call, not after: a session or global cap that is met returns a `BudgetError`, which the loop answers as a sentence and keeps out of memory rather than reporting as a breakage. The `usage` tool reports the whole picture, the CLI bar carries the session's spend, and the tray row carries today against all time. What smrti spends on its own entity extraction is outside all of this: those calls leave from the sidecar, not through the chain.
- **`internal/memory`** — smrti (Python) runs as a supervised REST sidecar: spawned, health-checked, restarted with backoff, auto-installed when missing (`install.go`). It is spawned with `ORT_DISABLE_TELEMETRY=1` for the reason the speech process is: smrti embeds on onnxruntime too, and the machine it posts to Microsoft is the same one. `Ambient` does per-turn recall→inject and store; everything degrades gracefully (empty recalls, dropped writes) when the sidecar is down. Who said something travels as `Source` (`user` or `agent`), which carries standing — smrti weights user-authored memory above agent-authored and only prunes the latter — and *which person* said it travels as a name on the content (`attribute`), because `Source` is a closed set the engine reasons about. Recall and store are scoped by channel and by **audience** — who can hear the reply, not who is speaking (`SpacePolicy.Scope`). Speaker identification separates each person's session history; confidentiality is a different axis, and the leak a per-speaker split cannot close is the owner asking something private while a guest is in the room, since that turn is theirs on every axis except the one that matters. So a turn somebody else can hear writes to `memory.shared_space` and reads only there, while a private turn writes to `space` and reads it plus `shared_space`: the user was present for all of it and should not have to be alone to remember their own conversation. The engine enforces the half that counts — a space reads its whole overlay but only ever mutates its own write space — so a private turn cannot write back into the shared one. Where the split is unavailable (no `shared_space`, or an engine that does not route spaces) a shared turn **recalls nothing** rather than being served from the one space holding everything; storing still happens, since what was said in company is not a secret from anyone who was there. The `space` parameter on `remember`/`recall`/`forget` cannot reach across that boundary either, which is what keeps the scope from being a suggestion. Partitioning by *person* remains a `Space` decision — whether the house shares what it knows — not a client-side one. `bridge.go` pays the partition's cost back by asking smrti to materialize the bridge between the two spaces (`POST /space_merge`), so a subject discussed once alone and once in company is not two islands neither side's graph expansion can cross. It runs on no schedule of its own: the engine already materializes bridges every tenth epoch, and a second timer in another repository would only drift from that one. What Factor adds is timing the engine cannot know — the merge fires on the turn that ends a gathering, when the two spaces have just finished diverging and nobody is waiting on a reply. It then waits for a quiet engine before starting, since the turn that ended the gathering is still being extracted, and gives up rather than compete with a machine that never settles; against an engine without the route it is absent entirely and the engine's own epoch is what joins the two halves. Memory is also exposed as deliberate tools (`remember`/`recall`/`forget`/`reflect`).
- **`internal/tools`** — the registry. A tool implements `Name/Description/Parameters/Execute` and registers once; users disable via `tools.disabled` config. A tool may declare itself safe to run beside the others in its batch (`tools.Parallel`, embedded as `ReadOnly` by the read-only suites); a batch where every distinct call declares it runs at once, since nearly everything here is waiting on a page, a file or the sidecar rather than on the CPU. One undeclared call serializes the whole batch — a file read running beside a mouse click is still a race — so order stays load-bearing wherever it was. `guard.go` (PathGuard) enforces workspace restriction with symlink resolution; exec has deny-patterns; secrets are scrubbed from every tool result at the registry layer, and every result is capped there too — one cap for every tool alike, including MCP servers, since a result that runs long is charged on every turn for the rest of the session and not just the one that asked for it. A truncated result says how much it withheld and how to ask for less, because a silent cut reads to the model as the whole answer. `ask.go` is how a turn puts a question to the user and waits for the answer, and the question goes wherever the user demonstrably is, which is the chat the turn came from: a turn dispatched off the bus from a conversational channel (`agent/ask.go`, gated on `Manager.Conversational` — a running connector that is not a `TurnRunner`, so the phone's SMS turns are excluded from a route that would dial the question) sends it as a message in that chat, and the session's next inbound message is claimed under the turn lock as the answer rather than steering — unless it is machine-authored (`bus.InboundMessage.System`, e.g. a job completion), which can never answer for a person. Under the gateway every other turn falls back to the desktop's own dialog on the active screen (zenity, kdialog or yad on Linux, System Events on macOS, an input box on Windows), while `factor chat` swaps in the terminal it already owns (`App.Ask`), where the options are numbered and the next line typed is the answer rather than a new message — the REPL is the only reader of stdin, so routing that one line is what keeps the two from fighting over it. Every path ends in the same three outcomes, an answer, a dismissal, or silence, so a user who is not at the machine costs the turn its timeout rather than hanging it. Other suites register into the same registry: `internal/browser` (CDP; two engines — the Chromium suite, plus an opt-in renderer-less Lightpanda fast path in `fast.go` that adds `browser_fetch` and only reads pages — over an engine `install.go` provisions itself, downloading Helium when the machine has no browser. A live DevTools port on 9222 wins over launching anything: the browser the user is logged into is the one sites that refuse automation still serve, and the managed fallback says so in the log. `readTemplate` ranks elements in three tiers — main content, then the controls over it, then site furniture — because document order on a listing returns two hundred nav links before the first result; it reads text from the main region, and every read states how much it withheld, since a truncation the model cannot see reads as an empty page. `browser_read` takes `filter`/`limit`, and `browser_scroll` exists for content that only loads on the way down), `internal/desktop` (X11/Wayland/macOS/Windows via helper commands; `MachineHasDisplay` probes the machine's display server rather than `$DISPLAY`, so setup over ssh targets the desktop the box is running, and `AdoptDisplay` hands that screen to a process that was started without one — systemd, launchd and a login autostart entry all pass no `DISPLAY`, which left every helper unable to open a display and `ask_user` telling a user sitting at the screen that the machine hasn't got one. `internal/app` adopts it once, onto the process, so the dialogs, the helpers, the browser and anything they spawn all inherit it; `grid.go`+`vision.go` add grid vision — `screen_view` overlays a battleship coordinate grid on the captured screen, `screen_zoom` magnifies a cell under a finer sub-grid, and `mouse cell=D4` resolves either grid back to native pixels, all pure Go image math with frames capped at 1568px), `internal/jobs` (background jobs whose completions re-enter the session), `internal/cron`, `internal/mcp` (mounts external MCP servers' tools at runtime), `internal/skills` (markdown skills, catalog-in-prompt with full text on demand; `skill_find` searches the public registry — skills.sh, over the credential-free `/api/search` its own CLI uses, since the documented `/api/v1` wants a Vercel OIDC token no personal agent can mint — and `skill_install` installs a hit by its `owner/repo/skill` slug from the snapshot endpoint, which is how a skill living three directories deep in a two-hundred-skill repository arrives without a clone or a GitHub token. `tools.skill_registry_url` repoints both at a mirror).
- **`internal/proxy`** — the `-p` flag, or the `proxy` config section. Routes this process and everything it spawns through any proxy by setting the standard environment variables, which is what makes `http.ProxyFromEnvironment` leave loopback alone (the memory sidecar and speech server keep talking directly) and what carries the setting into smrti and the voice shell, so their LLM calls land in the same capture. `--proxy-ca` adds a certificate authority on top of the system roots for a proxy that intercepts TLS, defaulting to the paths mitmproxy and Burp use; the system pool is read before the CA environment is exported, so only the children see the override — and it is exported under every name a child's TLS stack might read (`SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `GIT_SSL_CAINFO`), since git on Debian reads only the last of them. Inside the process the authority rides `http.DefaultTransport`, so a client that builds a transport of its own has to clone that one rather than start fresh: the self-upgrade did the latter, which made GitHub the one host Factor could not verify while every provider call went through the same proxy. One probe at startup reports the two failures that can mean nothing else — an authority this process cannot trust, and a proxy that does not answer — and stays silent about timeouts and DNS, which could be anything. The browser is deliberately not routed: it carries its own trust store. A flag only reaches the process someone typed it at, which left out the one that matters — the gateway systemd or the desktop starts at login is handed no flags at all, and everything unattended runs there — so `proxy.address` and `proxy.ca` say the same thing durably (`cmd/factor.resolveProxy`, read before any HTTP client or sidecar exists). A typed `-p` still wins, and it does not borrow the stored certificate: it may be pointing at a different proxy.
- **`internal/config`** — `~/.factor/config.json`, every key optional, `FACTOR_*` env overrides declared as struct tags. The gateway watches the file (`watch.go`): a change — hand-edited, or written by `config_set` from any session — reloads the daemon through the same settle-and-exec path an upgrade takes, so every key applies within seconds without dropping the turn in flight or restarting the sidecars, and the process that comes up names the changed sections in the chat it reports back to. A save that does not parse is warned about and retried, never applied. `log_level` (`FACTOR_LOG_LEVEL`) sets the lowest severity that reaches the log; it moves the default handler's threshold rather than replacing the handler, so the format every line is written in survives and the `slog.Debug` calls Go's default silently dropped become reachable. The agent's home is `~/.factor/workspace` (`AGENT.md`, `SOUL.md`, `USER.md`, `HEARTBEAT.md`, `instructions/`, `skills/`, `sessions/`, `cron/`).
- **`internal/tui`** — the interactive chat console (used by `cmd/factor`): owns the bottom rows of the terminal — a live activity line plus a prompt that stays editable while a turn runs — with replies landing above; falls back to plain lines without a TTY (pipes, `TERM=dumb`).
- **`internal/upgrade`** — self-update. Finds the newest GitHub release for this GOOS/GOARCH, verifies the download against the release's `SHA256SUMS`, and swaps the running binary (stage beside it, two renames, roll back on failure). Nothing here touches `api.github.com`, whose 60 requests an hour are counted per address and shared by everything behind it — a budget an office NAT can spend without Factor having asked for anything. The release workflow's asset names are fixed, so every URL is built rather than looked up: `/releases/latest` redirects to the newest tag, and that release's `SHA256SUMS` answers both whether it published a build for this machine and what the binary must hash to. Installing is not enough on its own — a running process keeps the code it loaded — so the gateway reloads: it waits for the turn in flight to be answered and its reply to drain off the outbound queue, shuts down cleanly, then execs the new binary at the path it was started from (same pid, so systemd never sees it stop). The reload is requested by the `upgrade` tool mid-conversation or by SIGHUP, which is how `factor upgrade` in a terminal reaches the daemon it just replaced. An exec keeps the pid and nothing else, so the outgoing process leaves a note in `~/.factor/restart-notice.json` naming the chat that asked (or, for a SIGHUP, the last one used); the process that comes up delivers it, deletes it, and ignores one older than 15 minutes — that is the "I'm back" line after an upgrade. The gateway still only *reports* a new version it finds on its own — once per version, into the last active chat; installing is always asked for. smrti is kept current by the same mechanism, in whichever of its two shapes this machine runs it. A container (`smrti.go`) is a registry lookup and a swap: the engine is found by the port it publishes (the container answering `memory.port` is by definition the one Factor talks to), the published image is pulled first, and the container is then recreated from its own spec — same volumes, same `-e` settings, same ports, with everything its old image supplied left to the new one — so the graph on disk and the way it was configured both survive. The swap waits for a quiet graph (`memory.IdleFunc`: nothing in flight and nothing finished in the last 15 seconds, health probes not counting) and rolls back to the container it replaced if the new one does not answer, so the engine is replaced under a live Factor with no restart of its own. A `factor upgrade` in a terminal cannot see what the daemon has in flight, so it asks over the gateway's health endpoint (`memory_idle`). A package install (`smrti_pkg.go`) — uv, pipx, pip or the private venv `factor init` falls back to, which is how most machines run it — measures PyPI's newest release against the version the engine reports over `/status`, or the one its own interpreter reads out of the installed package when the engine is down. The installer that made the install is the one that upgrades it, read off the path the executable resolves to: running a different one leaves two smrtis on the machine with whichever comes first on PATH answering, so an installer that is no longer here is reported rather than substituted. Installing is not enough on its own there either — a Python process keeps the modules it imported — so the engine is stopped once the graph is quiet and its supervisor brings it back on the new code. That is what `~/.factor/smrti.pid` is for: `keep_alive` hands the engine to whatever Factor runs next, so the process serving memory is not something a later run could find among its own children. It also settles what the stop meant, since a supervisor writes the replacement's pid down as it spawns it: a `factor upgrade` typed on a box with no daemon reports an engine stopped and waiting for the next run rather than a restart that failed. An engine nothing here spawned is left running with the new code waiting for its next start, and one answering on another host belongs to whoever runs it there.
- **`internal/wizard`** — the `factor init` interactive terminal wizard. Every step is verified live (provider completion, model list from the endpoint, Telegram `getMe`, carrier and voice credentials, a real page load through the browser), and the wizard provisions what is missing rather than reporting it: smrti, a browser, the desktop helpers the backend wants. Live engines are probed before an install is offered, so a smrti or voice shell running elsewhere is never offered a local install on top of it. The autostart step follows the same rule: saying yes installs the login entry itself (`internal/autostart` — a systemd user service where a user manager answers, an XDG autostart entry otherwise, a launchd agent on macOS, the Windows Run key), declining while one exists removes it, and the default mirrors what is already in place so Enter never changes how the machine boots.

Design intent: guardrails (PathGuard, deny-patterns, allowlists, redaction) protect against accidents and casual prompt injection — they are explicitly **not** a security boundary. Factor is a single-user personal agent.
